第一遍，从一份许可的去向读起

“许可”在这里是一次可成功获取的机会，不是像上一层的队列消息那样要复制的值。先用 134 认出对象字段，再按下面三段跟 Demo。txe_ 做参数检查，tx_ 核心才改变计数或处理等待；本配置的公开名映射（1391–1400 行）列出了它们的关系。

  1. 建对象：创建 semaphore_0，初值为 1（152–153 行） → 137 检查 → 136 写入初值。
  2. 取许可：共享入口先记循环次数，再 get（268–279 行） → 140 检查是否允许等待 → 139 减计数或加入等待环。
  3. 睡眠与归还：get 成功才睡两个 tick，再 put（281–289 行）。睡眠是独立的线程服务；归还才走 142 检查 → 141 加计数或交给等待者。

第一次可跳过带上限的 put、通知和统计；这些文件保留在完整目录中，但不是应用调用链。想检验自己是否把“许可数”和“等待人数”弄混，可以直接看两名线程的状态推演。

DEMO / 一份许可的交接

一边睡两个 tick，另一边却无限等待：等的不是同一件事

两次线程创建（106–120 行）用同一入口 thread_3_and_4_entry、不同的栈和输入值 3 / 4；二者优先级和抢占阈值都是 8，均无时间片并自动启动。输入值在 共享入口的循环开头（257–275 行）只用来区分该加哪个应用计数器。下面假定线程 3 先取到许可，并且线程 4 在它归还之前运行；这是一条源码允许的路径，不是上板观测，也不是固定调度次序。

以下每对数字均按 （可用许可数，信号量等待人数） 记录。睡眠的线程不等于在信号量等待环里的线程。

① 应用建好对象
（1，0）。136 记录初值 1，没有等待者；全局的已建对象数另算。这个 1 是起点，不是自动饱和的上限。
② 线程 3 取到后睡眠
（1，0）→（0，0）。139 返回成功，然后线程 3 在 sleep 的核心实现（158–189 行）进入 TX_SLEEP，设的是 2 个 tick。睡眠会让出 CPU，却没有执行 put，故不归还许可。这里的 tick 不应直接当成毫秒。
③ 线程 4 来取许可
（0，0）→（0，1）。许可已经用尽。线程 4 的 get 传 TX_WAIT_FOREVER，139 将它放进 semaphore_0 的等待环，状态为 TX_SEMAPHORE_SUSP。通用挂起是否启动超时定时器（129–142 行）解释了为什么这个 get 没有两 tick 的期限。
④ 线程 3 醒来并 put
（0，1）→（0，0）。两个 tick 到期让线程 3 可以恢复执行；直到它运行并调用 141，许可才被交付。141 摘下线程 4、记 TX_SUCCESS 并恢复它。线程 4 再获调度时从原来的 get 返回，不会重新排队，也不会对零再减一。
⑤ 对照：当时无人等呢？
若某次 put 时等待环为空，则走另一分支：（0，0）→（1，0），把许可留给未来一次 get。若当时有多人等待，一次普通 put 也只满足队首的一人，不是广播。

在 Demo 的状态判断（268–289 行）中，thread_3_counter、thread_4_counter 都是在 get 之前加一，不能当作已取得许可的次数。等待多久、谁先再次运行，不由这两个数或 ELF 中的函数地址给出。

读完之后 / SELF-CHECK

合上源码，判断三种情况

  1. 许可没有拿到，还是调用上下文不允许等？有效对象上不等待但无许可，139 核心返回 TX_NO_INSTANCE；上下文不允许却请求等待，140 包装先返回 TX_WAIT_ERROR，根本没查看许可数。
  2. 被恢复，一定表示拿到了吗？141 直接交付写的是 TX_SUCCESS；153 删除对象同样恢复等待者，写的却是 TX_DELETED。回到 get 时看的是线程里保存的结果，所以 Demo 会检查状态。对象管理等待环，能否马上运行由通用恢复与调度决定。
  3. 初值 1 是否足以防止重复 put？不足以。普通 put 不查所有者；若业务要求“目前可用的不超过一份”，144 检查正上限、143 核心按本次 ceiling 判断。它们限制计数，不会添加互斥锁的持有者或优先级继承语义；Demo 并没有调用它们。
