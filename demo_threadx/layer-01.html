类型、控制块与端口约定

线程 0 调用 tx_thread_sleep(10) 后，不是靠循环等完这 10 个 tick。谁替它记下这次等待？谁还能找到它的栈和入口？带着这个问题读下面五个头文件。

先认清三个东西

控制块记录“这是谁、现在什么状态”；线程栈存它的调用现场；内置定时节点记录它在等多久。第一遍不用通读两千多行的 tx_api.h，照每节给出的行号跳读即可。

文件 001 / 005

tx_port.h
临界区到底保存了什么？

已用 · 实际包含有效 422 行 / 物理 729 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/inc/tx_port.h ↗看裁剪版（有效 423 → 110 行）

通用内核需要屏蔽中断来安全地改就绪队列，但它不该写死某颗芯片的寄存器。这个端口头把两边接起来：一端提供 C 源码使用的类型和临界区宏，另一端给出此处理器、此编译器真正执行的动作。它没有选 NUCLEO 板，也没有配置 GPIO。

先沿着一对宏往下读

  1. 从 临界区的三个宏（610–612 行） 开始。TX_INTERRUPT_SAVE_AREA 声明保存原状态的局部变量；TX_DISABLE 把原状态存进去；TX_RESTORE 把这个值写回去。
  2. 再看 读取中断屏蔽状态（545–553 行） 与 屏蔽及恢复的内联函数（568–590 行）。本配置没有定义 TX_PORT_USE_BASEPRI，所以读写的是 PRIMASK。假设进入前已经屏蔽中断，退出时仍应保持屏蔽；这就是为什么不能把恢复简单写成“开中断”。
  3. 最后看 调度请求的名字映射（693 行）：本次 _tx_thread_system_return 映射到同一头中的 内联函数体（592–607 行）。其中写 ICSR 的 PendSV 挂起位，是请求异常，不是当场用 C 调用切换例程。真正的异常入口在 调度汇编标签（122–128 行）。

与下一份文件的关系：基础类型（113–123 行） 在这里确定。比如 ULONG 是 unsigned long；本次 ARM GNU 目标上它和指针都是 4 字节。下一节会用到这一点来读控制块的偏移，而不是按桌面电脑的类型大小猜。

不要被同名文件带走。目录里确实有 tx_thread_system_return.S。它只入了静态库，没有被本例 ELF 抽取；理解本例的临界区和 PendSV 请求，应读这里的内联实现。

文件 002 / 005

tx_api.h
线程控制块和线程栈是同一块内存吗？

已用 · 实际包含有效 1472 行 / 物理 2354 行条件宏与推荐裁前学习版源码common/inc/tx_api.h ↗看裁剪版（有效 1,473 → 817 行）

不是。Demo 先声明一个 TX_THREAD 对象（15 行），再另行分配线程栈并一起传给创建函数（80–86 行）。控制块是内核替这个线程保存的记录；栈是线程执行时存放调用现场的空间。两者由控制块里的指针联系起来。

第一次打开这个大头文件，只看三处

  1. 控制块前部（454–473 行）：tx_thread_stack_start / tx_thread_stack_end 给出栈边界，tx_thread_stack_ptr 保存建栈或切换时留下的栈位置，不是正在运行线程的实时 SP。这里的布局也是 C 与汇编的约定：本次 ELF 的调试信息给出该字段偏移 8 字节，与建栈汇编写回控制块的位置（127–131 行）一致。
  2. 线程状态、入口和内置定时节点（481–504 行）：入口函数指针与参数分别保存，tx_thread_timer 则直接嵌在控制块里。其类型 TX_TIMER_INTERNAL（370–395 行） 保存剩余 tick、超时回调及其参数。该成员不是应用创建的 TX_TIMER，也不是硬件 SysTick。
  3. 公共创建宏（1402 行）：从 Demo 的翻译单元看，tx_thread_create 在这里多传一个 sizeof(TX_THREAD)，进入 _txe_thread_create。包装层核对控制块大小（122 行），然后调用真正的创建实现（305–307 行）。与之对照，公共睡眠宏（1414 行）直接映射到 _tx_thread_sleep。不是所有公共名都走同一种包装。
回到 Demo：初始栈上的 PC 是 thread_0_entry 吗？

不是。创建实现先把用户入口及参数写进控制块（158–161 行），再用 _tx_thread_shell_entry 构造初始栈（202–210 行）。汇编把传入的函数地址放在初始 PC 的槽位（119–125 行）；等线程真正调度起来，外壳才经控制块调用用户入口（114 行）。分清“第一段要运行的内核代码”和“用户写的线程函数”，后面读汇编会容易很多。

文件 003 / 005

tx_thread.h
正在运行和接下来要运行，为什么是两个指针？

已用 · 实际包含有效 196 行 / 物理 534 行条件宏与推荐裁前学习版源码common/inc/tx_thread.h ↗看裁剪版（有效 197 → 107 行）

TX_THREAD 的结构体在上一份 tx_api.h 里。这份内部头解决另一个问题：单核调度器怎样在许多控制块之间选线程，把超时处理与线程关联起来。一个线程处于就绪状态，不等于它已经拿到了 CPU。

先区分两根指针

当前线程与选中线程的声明（308–321 行）中，_tx_thread_current_ptr 是当前线程，_tx_thread_execute_ptr 是调度器选中的线程。要找实际变量而不是 extern，看 初始化源文件里的定义（45–55 行）。再看抢占检查如何比较这两根指针（82–97 行）：当系统允许切换且两者不同，才走到向端口请求切换的调用点（125 行）。本配置的 TX_MAX_PRIORITIES 为 32，就绪优先级位图（343–348 行）只需一个 32 位元素；位表示该优先级有人就绪，不是某个具体线程的编号。

再找睡眠线程将来怎样被认出来

TX_THREAD_CREATE_TIMEOUT_SETUP（138–140 行） 在创建时把 _tx_thread_timeout 和标识这个控制块的参数一起放入线程的内置定时节点；实际调用点在 线程创建实现（202 行）。到期时，配对的取回宏（146–148 行）使回调能恢复正确的控制块指针。注意这是超时回调，与 thread_0_entry 这个用户入口不是同一指针。

怎样辨别公共头里的“默认实现”？本文件对系统状态给出的后备宏（123–125 行）有 #ifndef 保护。tx_api.h 已先包含端口头（121 行）；在本例 GNU 配置下生效的是 结合 IPSR 的端口版本（484–493 行），而不是在内部头里最后搜到的那行。

文件 004 / 005

tx_timer.h
没创建应用定时器，线程为什么还能睡 10 个 tick？

已用 · 实际包含有效 45 行 / 物理 215 行条件宏与推荐裁前学习版源码common/inc/tx_timer.h ↗看裁剪版（有效 46 → 29 行）

线程已经自带一个定时节点；这份头为它提供全局的计时结构。系统 tick 计数和定时槽数组（85–103 行） 是两件不同的事：前者记时，后者把等待到期的节点组织起来。数组有 32 个槽（56–57 行），当前槽指针与边界（109–116 行）用来环回。32 是槽数，不是最长睡眠时间。较长的等待会分段处理，源码可对照槽位选择（104–129 行）与超过一轮后的剩余 tick 处理（192–224 行）。

用 thread_0 的一次睡眠串起前四份头文件

  1. Demo 调用 tx_thread_sleep(10)（191–195 行）。本配置的实现先把状态置为 TX_SLEEP（162 行），再把 10 写入内置节点并挂起线程（174–189 行）。挂起路径把有限超时登记到定时系统（130–141 行）。这里没有调用应用定时器的创建接口。
  2. 低层 SysTick 入口（205–215 行） 调用端口时基处理；后者推进系统 tick 计数（91–99 行）。本例 TX_TIMER_PROCESS_IN_ISR 未定义，系统定时器线程的数据（140–149 行）存在。需要处理到期项时，到期处理恢复定时器线程（121–130 行）；不是直接在 SysTick 里运行线程的超时回调。
  3. 定时器线程取出回调和参数（268–269 行）并间接调用（307 行）。对睡眠线程，目标是上一节绑定的 _tx_thread_timeout，它检查线程仍处于睡眠状态（90–96 行），然后恢复这个线程（108–115 行）。恢复意味着重新有资格运行；何时获得 CPU，仍由调度决定。
别把两类线程加在一起。Demo 的 8 个应用线程之外，内核还创建了自己的 System Timer Thread（257–263 行）。也别仅由头文件把“10 个 tick”认定为实测毫秒数；硬件时基由启动支撑配置，并未在板上测量。

文件 005 / 005

tx_user_sample.h
为什么看得见一个 #define，它却没生效？

未直接用 · 配置模板有效 3 行 / 物理 306 行条件宏与推荐裁前学习版源码common/inc/tx_user_sample.h ↗看裁剪版（有效 4 → 4 行）

这个文件是给构建系统的配置模板，不是编译器实际包含的文件。它有 306 个物理行，却只有 3 个有效行：头文件保护的起始两行（68–69 行）和结束行（305 行）。例如在中断里处理定时器的开关（136–144 行）、事件跟踪的开关（228–234 行）都写在注释中。看见名字和 #define 字样，不等于当前目标启用了它。

按真实路径找配置，而不是按同名文件猜

  1. 配置时：CMake 选择默认模板并执行 COPYONLY（47–53 行），生成 out/tx-kernel/custom_inc/tx_user.h（附 A）。本例用的是默认模板，两份文件字节相同，但它们是两条不同的路径。
  2. 预处理时：构建目标设置包含目录与编译定义（53–58 行）；TX_INCLUDE_USER_DEFINE_FILE 来自编译命令的 -D。因此 端口头的条件包含（74–80 行） 选中 tx_user.h。本例 Demo 的包含顺序是 tx_api.h → tx_port.h → tx_user.h，不是 → tx_user_sample.h。
  3. 回看实际行为：模板没有启用 TX_TIMER_PROCESS_IN_ISR，所以第 004 份走定时器线程。模板也没有覆盖 TX_MAX_PRIORITIES，其值 32 来自 端口默认值（128–130 行）。如果关心 tick 频率，公开头的参考常量（305–310 行）和真正设置 SysTick 的启动代码（129–135 行）要分开读。
为什么目录要同时留两条？按“本次直接包含”筛选时，应该看附 A 的 tx_user.h；按“读全上游”筛选时，应该找到这里的模板。前者属于 6 份构建与应用支撑，后者属于 208 份上游源码，谁也不能替代谁。

读完之后 / SELF-CHECK

不用背宏，试着追两条线

  1. 从创建追到第一次运行：公共创建宏 → 错误检查 → 控制块保存用户入口 → 汇编保存初始栈指针 → 线程外壳调用用户入口。能指出这两种“入口”分别在哪里保存，就读懂了控制块与端口的分工。
  2. 从睡眠追到重新就绪：创建时绑定超时回调 → 睡眠时登记 10 个 tick → 定时器线程处理到期节点 → 恢复正确的线程。能解释为什么恢复不等于马上执行，就能继续读调度层。
本层标记和行号是怎么核对的？

沿用 demo_threadx-01/relink-01 的 ELF 和 map，复核固定提交、逐文件哈希、编译依赖，并用原 GCC 编译参数只做预处理。Demo 直接包含公开头；线程创建实现包含线程内部头；定时器初始化包含定时器内部头。4 份“已用”不表示 Demo 自己显式包含了这四个头，更不表示每个条件分支都被执行。

控制块栈指针的偏移也与 ELF 的 DWARF 成员位置交叉核对。站内文章可离线阅读；固定提交的上游行号链接需要联网。这些是构建和静态源码证据，不是上板结果，也不是 VS Code 逐项 F12 验收。
