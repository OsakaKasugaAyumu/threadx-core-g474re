启动与链接支撑

在这个 ELF 里，_tx_initialize_low_level 的第一条指令在 0x000000D0，复位处理函数却在更高的 0x000051FC。哪个先执行？不要按地址大小猜。读向量表的前两个字，再沿着分支去找 main。

四份文件，分三个时刻读

  1. 链接时：B1 链接脚本定下向量表的位置、哪些初值留在 FLASH、栈顶在哪里。它是给链接器读的，不是复位后的第一段程序。
  2. 进入 C 之前：处理器从B2 向量表取初始主栈指针（MSP）与复位入口。reset_handler 跳到B3 的 _start，由它准备 C 运行环境并调用 main。
  3. 进入 C 之后：Demo 的 main（58–63 行） 调用 tx_kernel_enter()。这才经第 13 层的通用内核入口调用B4 低层初始化。B4 返回后，内核继续高层初始化、应用定义和首次调度。

附 B / 文件 B1

demo_threadx.crt0.ld
把启动代码需要的地址交给链接器求值

已用 · 实际链接脚本有效 112 行 / 物理 153 行条件宏与推荐裁前学习版源码relink-01/demo_threadx.crt0.ld看裁剪版（有效 113 → 113 行）

先找本次实际生效的脚本。成功链接的 relink-01/link.rsp 用 -T 指定的是这份 demo_threadx.crt0.ld，而不是 ST 目录里名称相似的 sample_threadx.ld。它保留示例的内存布局，并补齐原启动汇编读取的段边界与装载地址。下面的行号均指本地 B1；这是构建文件，没有对应的上游原件链接。

向量表放哪里？
第 5–29 行
示例将 FLASH 放在 0x00000000、容量 4 MiB，将 RAM 放在 0x20000000、容量 8 MiB。先保留 .vectors，再安排 .text，其中保留了复位入口和 CRT 所在的 .init。这些是示例链接区域，不是 G474RE 的存储器参数。
初值放哪里、变量在哪里用？
第 56–61、75–110 行
.data 的装载地址（LMA，初值在镜像中的位置）是 0x00005414；运行地址（VMA，C 程序访问的位置）是 0x20000000，长度 0x6C，即 108 字节。链接器给出两处地址，真正搬这 108 字节的是 B3。.text 和只读数据在此镜像中原地使用，不因 CRT 有复制调用就会被搬入 RAM。
没有内容的段也要有名字吗？
第 112–123 行
要。原 CRT 引用 __fast_load_start__、__fast_start__ 和 __fast_end__。本次没有 .fast 输入，起止运行地址同为 0x2000006C。这样既能解析符号，CRT 也能从零长度判断“不必复制”。
初始栈顶由谁给出？
第 11–13、125–152 行
脚本划出 .bss、128 字节的兼容堆和 1,024 字节的系统栈；__stack_end__ 在本 ELF 为 0x200035B8。这是这段栈的上界，不是全部 RAM 的末端，也不是某个应用线程的栈指针。

对照：在 B2 看栈顶怎样进入向量表，在 B3 看段边界怎样变成复制长度。链接符号给出地址，不是另建一个保存该地址的 C 变量。

本例使用证据

以 relink-01/link.rsp 核对唯一的 -T 输入，以同目录的 demo_threadx.map 核对内存区域和段，以 ELF 段表、装载段与符号表核对地址。早先的链接日志报了 11 个缺失的 CRT 符号，包括 __text_load_start__ 和 __fast_end__；最终 ELF 已解析它们。B1 的 SHA-256 是 58df5cdec8b8c7783d02b26e38f5e7dd1d7e7dd026edc7465bf1838ae50c2800。它是链接脚本，不会有自己的目标文件。

cortexm4_vectors.S
复位和异常发生时，处理器跳到哪里？

已用 · 直接链接有效 69 行 / 物理 77 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/example_build/cortexm4_vectors.S ↗看裁剪版（有效 70 → 70 行）

先把 cortexm4_vectors.S 的向量表开头（12–21 行）当作一排 32 位数据读，而不是顺序执行的汇编。B1 把 _vectors 放在地址零；这份 ELF 的 .vectors 有 204 字节，共 51 个表项。读下面四格，就能区分“存一个地址”和“在那个地址执行”。

表项 0 · 偏移 0x00
0x200035B8：从 B1 的 __stack_end__ 取得的初始 MSP。它是一个栈地址，不是函数。
表项 1 · 偏移 0x04
0x000051FD：reset_handler 的 Thumb 入口值。最低位表示 Thumb 状态，第一条指令在 0x000051FC。链接选项 -e reset_handler 也使 ELF 入口字段指向它；芯片复位按向量表取值，并不读取 ELF 文件头。
表项 14 · 偏移 0x38
0x000006BD → __tx_PendSVHandler。实现是第 02 层调度汇编中的 PendSV_Handler 同址入口，不在向量表文件里。
表项 15 · 偏移 0x3C
0x00000135 → __tx_SysTickHandler。这是 B4 的 SysTick 中断入口，它才会调用内核的 _tx_timer_interrupt。

复位处理函数（70–74 行）只有跳向 _start 的分支；那里关于 PLL 的文字是注释，不是时钟初始化代码。SVC、PendSV、SysTick 与外部中断槽（29–68 行）也要按实际标签判断：本例的 SVC 落到原地循环（172–177 行），不是首次调度入口；35 个外部中断槽都指向 __tx_BadHandler，并非某块 STM32 的完整外设 IRQ 表。

本例使用证据

cortexm4_vectors.S.obj 同时出现在链接响应文件和 map 的直接 LOAD 记录。对象中复位分支的重定位目标是 _start；最终 ELF 中以上四个向量字已解析为具体值。map 还记下：恰是该对象对 __tx_PendSVHandler 的引用，使链接器从 libthreadx.a 抽取了 tx_thread_schedule.S.obj。

附 B / 文件 B3

cortexm4_crt0.s
在 main 之前，先让 C 的变量有正确的初值

已用 · 直接链接有效 92 行 / 物理 119 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/example_build/cortexm4_crt0.s ↗看裁剪版（有效 93 → 93 行）

CRT 是 C 运行时启动代码。_start 起点（11–20 行）先屏蔽可屏蔽中断，再把 B1 的 __stack_end__ 装入 SP。此时既没有应用线程，也还没调度。最值得顺着读的是接下来三个动作：

  1. 为有初值的变量搬数据。六组复制调用（16–40 行）依次处理 .data、.text、.fast、构造表、析构表和只读数据。每组给出「装载起点、运行起点、运行终点」。复制助手（91–104 行）在源与目标相同或长度为零时直接返回，否则逐字节复制。因此本镜像确实需要搬的是 B1 列出的 .data；.text 原地使用，.fast 为空。
  2. 为零初值的变量和运行库准备 RAM。清 .bss 并初始化兼容堆（43–56 行）：.bss 用零填充，不从 FLASH 复制初值；堆开头两字分别写零和堆区长度。这个堆不是 Demo 的 ThreadX 字节池：应用另用 memory_area 创建字节池（68–75 行）。随后遍历构造函数表（58–70 行）；本 ELF 的 __ctors_start__ 与 __ctors_end__ 相等，没有构造函数需要调用。
  3. 最后才进 C。装入 main 地址并用 BLX 调用（72–85 行）。因此在此文件找直接写作 BL main 的指令会漏掉这条边。若 main 返回，CRT 留在退出循环；而本例的 main 正常路径是进入内核，不会回到这里。

同一份代码，两种文件名大小写：本机编译输入是小写扩展名 cortexm4_crt0.s，固定上游提交中是 cortexm4_crt0.S。两者 Git blob 相同；“本仓库源码”使用小写 .s，上游链接使用大写 .S。

本例使用证据

map 直接加载 cortexm4_crt0.s.obj。其 .init 段对 main 的绝对地址重定位与上述间接调用相符；同段对 __data_load_start__、__bss_end__ 等的引用均由 B1 满足。最终 ELF 的 _start 指令地址是 0x00005200；复位分支跳到这里，不是直接跳到 main。

tx_initialize_low_level.S
把向量表、系统栈与时钟接到 ThreadX

已用 · 直接链接有效 99 行 / 物理 233 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/example_build/tx_initialize_low_level.S ↗看裁剪版（有效 100 → 88 行）

名字里有 low_level，它却不是复位入口。本例的 main 经 tx_kernel_enter 宏（1207–1213 行）到达通用内核入口的初始化分支（101–125 行），由该分支调用 _tx_initialize_low_level。B4 完成下面这些准备便返回；它自己不调用高层初始化，也不创建应用线程。

  1. 传递内存与系统栈地址。关中断、写空闲内存指针、设置 VTOR 并保存系统栈顶（96–120 行）。_tx_initialize_unused_memory 取 B1 的 __RAM_segment_used_end__ + 4，按本 ELF 推算是 0x200035BC；这不是指针变量本身的地址。VTOR 指向 B2 的 _vectors，而 _tx_thread_system_stack_ptr 保存的是从表项 0 读出的值 0x200035B8。这里是保存栈顶，不是再次设置 SP。通用入口稍后才把空闲地址传给应用定义函数（131–142 行）。
  2. 给 tick 一个时基。本文件先设置 DWT 周期计数使能位（122–127 行）；内核节拍则来自另一个硬件单元 SysTick。本例汇编常量（41–42 行）假设输入时钟为 6 MHz；写 SysTick 重装值、控制位和异常优先级（129–147 行）时，重装值为 59,999（0xEA5F），控制值 0x7 选择处理器时钟、允许中断并启动计数。每次计 60,000 个时钟，仅在 6 MHz 假设成立时才是 100 Hz、每 tick 10 ms。tx_api.h 的 tick 参考常量（304–310 行）不会替芯片配置 PLL；写了 SysTick 也不表示此时已经放开中断。
  3. 把两类异常送到不同实现。本文件的 SysTick 入口（201–220 行）保存返回现场、调用 _tx_timer_interrupt、恢复后异常返回；内核 tick 汇编（85–96 行）递增软件时钟。PendSV 则是另一条路：通用入口完成应用定义之后才调用调度器，调度入口放开中断并挂起 PendSV（89–117 行），处理程序在 CPU 移植的调度汇编（120–130 行）中。不能因为 B4 声明了 __tx_PendSVHandler 就把它当作这里定义的函数。
本例使用证据

tx_initialize_low_level.S.obj 是直接链接输入；它的代码段只有一条对函数的 R_ARM_THM_CALL 重定位，目标为 _tx_timer_interrupt，来自 SysTick 入口而非初始化函数体。map 记录这条引用使内核的 tx_timer_interrupt.S.obj 被抽取。ELF 中 SysTick_Handler 和 __tx_SysTickHandler 同址；以上常量与向量表可静态核对，不是上板实测的中断频率。

附 B 小结

这份 ELF 能证明什么？

它能证明复位向量指向谁、CRT 和链接脚本约定的地址是否一致、SysTick 和 PendSV 最终接到哪份代码。读到某个符号时，先问它是链接器给出的地址、表中的函数指针，还是已经能执行的指令；这样就不会把 __stack_end__ 当成变量，把向量表当成函数，或把 low_level 当成复位后的第一步。

这不是 NUCLEO-G474RE 的板级固件。链接区域、初始时钟假设和外部 IRQ 槽都是本示例的条件；链接成功不等于这些条件在板上成立。本页只核对既有 ELF、map 和原件，没有烧录、运行或测量。正文可离线阅读；行号链接指向固定上游提交，不代替 VS Code 逐符号跳转实测。
