附 A / 文件 A1

tx_user.h
编译器实际包含的用户配置头

已用 · 实际配置头有效 3 行 / 物理 306 行条件宏与推荐裁前学习版源码out/tx-kernel/custom_inc/tx_user.h看裁剪版（有效 4 → 4 行）

只有第 68、69、305 行有效：前两行检查并定义头文件保护宏 TX_USER_H，最后一行结束这个条件块，防止同一翻译单元重复展开文件。其余是注释或空行。这个头允许用户覆盖配置，但本例没有在这里覆盖任何选项。它没有函数体，不单独编译成 .obj，也不需要在 ELF 中找到一个叫 tx_user.h 的函数。

从模板到应用：哪个环节读了哪个文件？

  1. CMake 在配置时选文件。本次配置日志记为 Using default tx_user.h file。默认输入与 COPYONLY 规则（47–53 行）选取 005 · common/inc/tx_user_sample.h，把文件原样复制到构建目录并命名为 tx_user.h。这一步不解析 OIL/DTS，不生成任务对象或 C 实现。
  2. 编译命令决定要不要读。构建目标公开的包含目录与编译定义（53–58 行）让内核与使用它的 Demo 都得到 custom_inc 搜索路径和 -DTX_INCLUDE_USER_DEFINE_FILE。它的意思只是“包含用户头”；这个宏来自命令行，不是由 tx_user.h 定义自己。
  3. 预处理器找到实际路径。Demo 包含 tx_api.h（5 行） → tx_api.h 包含 tx_port.h（119–121 行） → M4/GNU 端口按条件包含 tx_user.h（72–80 行）。内核中的线程创建实现（26–31 行）也从 tx_api.h 接入。两条路径最后读到同一个 A1，而不是直接包含上游模板。

为什么目录留两项？005 是 CMake 的输入，属于上游 208 份，标记「未直接用 · 配置模板」；A1 是编译器的输入，属于范围外的 6 份支撑，标记「已用 · 实际配置头」。本次两份文件逐字节相同，但它们回答的是不同的问题。

从三个宏看出：注释、默认值和实际行为不是一回事

下列行号用同字节的上游模板对照 A1。链接到模板是为了查看相同行的文字；构建目录中的 A1 本身没有上游原件链接。

TX_MAX_PRIORITIES
32 从哪里来？
模板里数值 32 位于注释块内（106–115 行），不生效。真正生效的是端口在未定义时给出的默认值 32（125–130 行）。它决定每个优先级一个就绪链表头（123–126 行）；与本构建 ELF 中 _tx_thread_priority_list 的 128 字节相符（32 个 4 字节的指针）。这不是“最多只能建 32 个线程”。
TX_TIMER_PROCESS_IN_ISR
线程 0 的超时谁处理？
Demo 的线程 0 休眠 10 个 tick（188–195 行）。A1 里直接在中断中处理超时的开关（136–144 行）被注释，编译命令也未定义它。因此内核创建系统定时器线程（242–262 行）；有到期项时，到期处理分支唤醒该线程（106–130 行）。不是没有 tick 中断，而是不用在 ISR 里完成全部到期处理。可接着读第 05 层的定时器线程入口。
TX_ENABLE_EVENT_TRACE
能搜到就会记录吗？
不会。Trace 开关也在注释中（228–234 行）；本例未从别处启用。tx_trace.h 的未启用分支（56–64 行）把事件插入等宏定义为空。所以即便内核源码中能看到记录点，也不能据此认定 Demo 采集了事件。回看第 12 层的记录宏。
本例使用证据：为什么确定 A1 被包含？

先用 relink-01/demo_threadx.map 确定最终链接涉及的 67 个翻译单元（静态库抽取 63 个，直接输入 4 个），再查同一构建的 ninja -C out -t deps。有 61 个单元的有效依赖记录列出 A1：60 个内核 C，加上 samples/demo_threadx.c。其余 6 个汇编输入没有这条记录；这 67 个单元中没有一个列出 common/inc/tx_user_sample.h。61 是包含者的数量，目录里的配置头仍只计 1 份。

out/compile_commands.json 可交叉核对 Demo 和 tx_thread_create.c 的编译参数：二者都有上述 -D 和同一构建头目录。若编辑器打开了另一份同名文件，先核对当前翻译单元的编译命令和实际依赖；这些证据不等于已实测 VS Code 的 F12。

实际头与模板的 SHA-256 相同：1df83392bf11519ba09c9523d7b23ac4f7b960855c289174972bd13b9e3a4f35。同字节模板中的保护宏（68–69 行）和结尾行（305 行）可逐行对照。头文件的「已用」根据包含依赖判定；ELF 里的 _tx_timer_thread_entry 只用来印证所选定时器路径，并非证明头文件被包含的依据。
