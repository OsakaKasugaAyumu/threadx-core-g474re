读 _tx_thread_interrupt_disable 时只盯住 r0：它不是错误码，而是调用者进临界区以前的中断屏蔽状态。独立汇编入口（68–78 行） 在默认分支里先读 PRIMASK，再屏蔽可屏蔽中断，最后把旧值留在 r0 返回。NMI 和 HardFault 不受这一位屏蔽。另一分支用 BASEPRI 调门限，本例没有选它。

第 02 层 / 文件 007

tx_thread_interrupt_restore.S
退出临界区，是恢复旧状态，不是打开中断

未直接用 · 本配置未编译有效 12 行 / 物理 76 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_interrupt_restore.S ↗看裁剪版（有效 13 → 9 行）

恢复入口（68–75 行） 把输入 r0 当作先前保存的状态，写回 PRIMASK；选用门限方案时则写回 BASEPRI。这里既不重新推断进入前的状态，也不约定写入的值总是零。本例的 TX_RESTORE 走 端口头内联实现（568–575 行），独立汇编未编译。

用两层临界区走一遍

假设一开始 PRIMASK=0。外层保存 0 并屏蔽，内层保存 1。退出内层时写回 1，外层仍受到保护；退出外层才写回 0。若把内层恢复换成无条件开中断，外层还没更新完的数据就可能被 ISR 看到。关键不在嵌套计数，而在每一层各自保留进入时的值。

第 02 层 / 文件 008

tx_thread_interrupt_control.S
这次由调用者决定要设置什么状态

未直接用 · 仅入静态库有效 16 行 / 物理 79 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_interrupt_control.S ↗看裁剪版（有效 17 → 11 行）

上一对入口做的是“屏蔽”和“恢复”。_tx_thread_interrupt_control 做的是交换：比较输入和返回寄存器（68–78 行），进入时 r0 是新状态，旧状态暂存在 r1；写入新状态后，返回时 r0 已换成旧状态。它不会替调用者保存旧值到控制块。

从 公开 API 的名字映射（1361–1367 行） 可以追到这个入口。本例 Demo 没有调用 tx_interrupt_control，但库里已编入这个汇编对象。对比 006、007：三者在最终 ELF 都找不到，原因却不同；只有这一份在静态库中能找到独立实现。

第 02 层 / 文件 009

tx_thread_stack_build.S
第一次运行的线程，哪来的“现场”可以恢复？

已用 · ELF 抽取有效 32 行 / 物理 133 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_stack_build.S ↗看裁剪版（有效 33 → 33 行）

线程从没运行过，自然没有被中断过。ThreadX 的做法是先造出一份符合 PendSV 恢复顺序的栈帧。创建时登记用户入口及参数（158–161 行） 与 调用端口建栈（207–210 行） 要对照读：传给汇编的 r0 是线程控制块（TCB）指针，r1 是内核外壳 _tx_thread_shell_entry，不是 Demo 的用户入口。

从保存的栈指针往高地址读：17 个字，68 字节

找到栈顶并预留空间（96–100 行） 从 TCB 的 +16 取栈的高端地址，先向下对齐到 8 字节，再减去 68。以下偏移相对于这个减完后的地址，不是相对于 TCB。

  • +0：0xFFFFFFFD，异常返回码（EXC_RETURN）。PendSV 最后用它返回线程模式，选择进程栈 PSP，并使用基本异常帧。
  • +4 至 +32：八个槽位存 r4–r11，初始为零。它们由 PendSV 软件恢复，不在处理器自动恢复的基本帧里。
  • +36 至 +52：r0–r3 和 r12；+56：线程自己的初始 LR，填 0xFFFFFFFF 作无效返回地址，与 +0 的异常返回码用途不同。
  • +60：初始 PC 指向内核外壳；+64：初始 xPSR 置 Thumb 状态位。两者都属于异常返回时由处理器恢复的部分。

对应源码：逐槽填初值（104–125 行） → 把完成后的地址写回 TCB 的 +8（130 行）。在 TCB 前部的字段（461–468 行） 找到 tx_thread_stack_ptr；再到 外壳间接调用用户函数（114 行），这才把执行权交给 Demo。一个控制块记录用户入口，一张栈帧记录首次执行的 PC，两者并不矛盾。

自测：68 字节是这个端口为新线程准备的初始现场，不是“每次进中断必压 68 字节”，也不是应用线程所需的全部栈空间。

第 02 层 / 文件 010

tx_thread_context_save.S
名字叫 context_save，为什么里面没保存 r4–r11？

未直接用 · 仅入静态库有效 12 行 / 物理 80 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_context_save.S ↗看裁剪版（有效 13 → 8 行）

先问是谁在“保存”。Cortex-M 接受异常时，硬件就会保存基本现场，包括返回 PC 和 xPSR；被打断的线程使用 PSP 时，该帧在它的 PSP 上，进入 Handler 模式后处理程序用的是主栈 MSP。真正换出线程时，硬件没替内核保存的 r4–r11 由 012 的 PendSV 另外保管。

检查保存入口的条件块（68–79 行）：只有启用执行通知或分析时才临时保护寄存器、调用 _tx_execution_isr_enter。本例这两个选项均未开；静态库反汇编里函数本体只返回调用者，最终 ELF 也没有抽取它。不要把这个可选 ISR 入口当成每个中断都必须经过的代码。

第 02 层 / 文件 011

tx_thread_context_restore.S
从 ISR 退出，是谁负责“恢复”？

未直接用 · 仅入静态库有效 15 行 / 物理 82 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_context_restore.S ↗看裁剪版（有效 16 → 8 行）

退出钩子入口（72–81 行） 是上一份的另一半：启用通知或分析时才调用 _tx_execution_isr_exit。本配置下，静态库中的函数本体也只是返回，没有装载线程的 PSP，最终 ELF 未抽取它。

看本例的 SysTick 包装入口（205–220 行）：包装器自己保留 LR、调用 tick 处理函数，再恢复 LR 返回，并不调用这个独立实现。同样是 BX LR，若 LR 是普通子程序返回地址，就回调用者；若 LR 是处理器提供的异常返回码，才由硬件恢复异常现场。读汇编时先弄清 LR 从哪来，不要按指令名字猜。

第 02 层 / 文件 012

tx_thread_schedule.S
PendSV 怎样把 CPU 交给另一个线程？

已用 · ELF 抽取有效 168 行 / 物理 325 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_schedule.S ↗看裁剪版（有效 169 → 95 行）

本文件有两种入口。内核启动调用调度入口（153 行） 只发起首次调度；异常向量表（32–33 行） 让处理器随后进入 __tx_PendSVHandler，与 PendSV_Handler 同址。启动支撑给 PendSV 和 SysTick 分配不同优先级（146–148 行）。前者可以挂起，等优先级允许再接管；这不是 C 函数直接调用异常处理器。

  1. 发出第一次请求。首次调度入口（83–117 行） 清抢占禁止计数，本配置还清浮点上下文活动位 FPCA；允许中断，向 ICSR 写 PENDSVSET，执行屏障后等待异常。这个等待循环不是轮询就绪线程的调度算法。
  2. 保存旧线程。取 current 与旧 PSP（153–188 行）：若 _tx_thread_current_ptr 为空（首次调度），直接跳过保存。否则保存 r4–r11 和异常返回码，把新栈指针写回旧 TCB 的 +8，有剩余时间片时也保存它。浮点分支见下。
  3. 接收已选好的线程。把 execute 变成 current（196–226 行）：_tx_thread_execute_ptr 是内核已选的下一位，_tx_thread_current_ptr 是当前运行者。本段不是扫描优先级选举；它接收选择结果，更新运行次数及活动时间片。若没有就绪者，进入 空闲等待分支（256–291 行）；本配置未启用 TX_ENABLE_WFI，不能把它说成一定执行睡眠指令。
  4. 恢复新线程。从新 TCB 的 +8 装回 PSP（237–250 行）：先取异常返回码，再按需恢复浮点和 r4–r11，把剩余帧的地址写入 PSP。最后 BX LR 触发硬件异常返回。对于新线程，硬件读到的 PC 正是 009 写入的外壳地址。
M4F：启用硬浮点，是不是每次都要搬浮点寄存器？

不是。编译时的 __ARM_FP 让保存、恢复浮点的指令出现在 ELF；运行时还要检查 EXC_RETURN 的第 4 位。为 0 表示扩展帧，端口才额外搬 s16–s31；为 1 是基本帧，跳过。新线程的初始返回码 0xFFFFFFFD 正属于后一种。直接对照 保存侧条件（165–174 行） 和 恢复侧条件（237–246 行）。

第 02 层 / 文件 013

tx_thread_system_return.S
请求调度，不等于当场切走

未直接用 · 仅入静态库有效 24 行 / 物理 93 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_thread_system_return.S ↗看裁剪版（有效 25 → 18 行）

调度请求的独立汇编入口（70–92 行） 把 PENDSVSET 写入 ICSR，将 PendSV 标为待处理；它本身不搬任何线程栈。随后读 IPSR 判断来源：若在 Handler 模式则直接走返回路径；若在线程模式，本配置的分支先记下 PRIMASK，短暂允许中断，再恢复原屏蔽状态。何时能进 PendSV 取决于异常优先级和屏蔽状态。

从 通用 C 的抢占检查调用点（125 行） 找实现时，别停在同名汇编：当前端口的宏映射（693 行） 指向 内联的调度请求实现（592–607 行）。因此本例确实能请求调度，独立 .S 又确实只入库、未被 ELF 抽取。这两个结论可以同时成立。

第 02 层 / 文件 014

tx_timer_interrupt.S
一次 SysTick 之后，是否一定要换线程？

已用 · ELF 抽取有效 85 行 / 物理 255 行条件宏与推荐裁前学习版源码ports/cortex_m4/gnu/src/tx_timer_interrupt.S ↗看裁剪版（有效 86 → 84 行）

不一定。向量槽（32–33 行） 指向启动支撑的 SysTick 包装器（205–220 行），它才调用本文件的 _tx_timer_interrupt。这个例程负责推进时间、发现需要处理的事件；搬线程栈的是 PendSV。

  1. 推进系统时钟和活动时间片（93–124 行）：全局 tick 加一；当前有非零时间片才递减，减到零置时间片到期标志。不是给每个线程各减一次。
  2. 检查当前定时器槽（134–174 行）：槽非空时置定时器到期标志；槽空时才在此处前移指针，到表尾就绕回。不是每个 tick 扫一遍所有定时器。
  3. 按标志分派处理（183–226 行）：定时器侧调用 _tx_timer_expiration_process；本配置走 恢复系统定时器线程（125–130 行） 的路径，不是由这里直接调用应用超时回调。时间片侧调用 _tx_thread_time_slice。时间片处理后的检查（226–238 行） 只在允许抢占且 current 与 execute 不同的情况下，才在此处挂起 PendSV。
回到 Demo：线程 1 和 2 的创建参数（95–104 行） 都把优先级设为 16、时间片设为 4。看 通用 C 中同级轮转的条件（115–143 行）：若另一个线程正阻塞，本优先级并没有第二个就绪者，就不能预测“两者每 4 tick 必然互换”。

读完之后 / SELF-CHECK

合上汇编，试着讲清两次交接

第一次启动：创建函数把用户入口记在 TCB → 建栈函数把外壳地址放在初始帧的 PC 槽 → 首次 PendSV 没有旧线程要保存，只装入已选线程的栈 → 硬件异常返回到外壳 → 外壳取出用户入口与参数。若忘了是哪两种入口，回看 009 的 +60 槽。

稳态的一个时间片：SysTick 包装器 → tick 例程递减时间片 → 到期才进通用 C 检查同级就绪者 → 需要且允许抢占时挂起 PendSV → 保存旧 PSP，恢复新 PSP。若同级就绪者只有当前线程，这条链可以停在时间片处理，不产生线程交接。

对照本例最终 ELF：入口和调用点

沿用 demo_threadx-01/relink-01，以下为反汇编地址，不是上板执行记录。建栈调用在 0x458e，目标 _tx_thread_stack_build 在 0x4b30；首次调度调用在 0x8d0，目标 _tx_thread_schedule 在 0x690。PendSV_Handler 与 __tx_PendSVHandler 同在 0x6bc。

SysTick_Handler 与 __tx_SysTickHandler 同在 0x134，0x136 调用 _tx_timer_interrupt（0x750）。tick 中 0x7a8 调用到期处理、0x7b2 调用时间片处理。PendSV 中 0x6d8 和 0x714 有浮点寄存器组的存取指令，这不证明运行时一定走该分支。
