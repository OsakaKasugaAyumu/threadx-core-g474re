第十三层 / 从内核回到 Demo

通用初始化与内核入口

线程 1 和 2 创建时都选了自动启动，可它们要用的队列是在后面才创建的。它们会抢先访问一个还不存在的队列吗？顺着 main 找到首次调度的位置，就能把“已经就绪”和“已经执行”分开。

先走一遍本例，再按 205–208 读文件

Demo 的 main（58–63 行） 只调用 tx_kernel_enter()。下面是这份 Cortex-M4/GNU 构建的调用关系，不是按文件编号执行：

  1. 进入内核。208 · kernel_enter 判断是否已经提前初始化；本例没有，先调端口的 low_level，再调206 · high_level。
  2. 交给应用建对象。返回到 208，由它调用 tx_application_define。Demo 在这里建内存池、线程、队列等对象；这不是任何一个线程的入口。
  3. 开始运行线程。应用定义函数返回之后，208 才调用 Cortex-M4 的调度入口。首次切换由 PendSV 完成。

205 给两条初始化路径约定状态值；207 是另一种启动方式的入口，不插在上述三步之间。

第 13 层 / 状态与声明 / 文件 205

tx_initialize.h
初始化进行到哪一步？

已用 · 实际包含有效 27 行 / 物理 113 行条件宏与推荐裁前学习版源码common/inc/tx_initialize.h ↗看裁剪版（有效 28 → 15 行）

先辨认变量：这里的三个常量描述内核启动到哪一步，不是某个线程的就绪或挂起状态。它们定义在状态常量和三个内部函数原型（54–65 行）；保存状态的变量则在线程组件头中声明（336–340 行），在线程组件 C 文件中定义并赋初值（68–74 行）。

TX_INITIALIZE_IN_PROGRESS
0xF0F0F0F0。本例启动时的初值；调用应用定义函数时仍处于初始化阶段。
TX_INITIALIZE_ALMOST_DONE
0xF0F0F0F1。可选的 kernel_setup 留下的记号：低层和组件初始化已做过，应用定义和调度仍未开始。
TX_INITIALIZE_IS_FINISHED
0。应用定义函数返回后由 kernel_enter 写入；不是“第一个线程已经运行”的证明。

顺着指针找定义：INITIALIZE_DECLARE 与 _tx_initialize_unused_memory（94–110 行） 在未定义 TX_INITIALIZE_INIT 时给出 extern 声明。本构建的存储定义在 high_level.c 的文件作用域（47–52 行）；写入指针值的是低层汇编（102–107 行），读出并传给应用的是 kernel_enter（131–142 行）。头文件不负责分配一块内存。

顺着宏找实现：本头为端口数据及初始化钩子（68–89 行）提供空的后备定义。但要先看 tx_port.h：本端口的 TX_PORT_SPECIFIC_POST_INITIALIZATION（508–520 行） 不是空操作，而是递增 _tx_thread_preempt_disable，防止应用仍在建对象时就发起线程切换。

本例使用证据

在 Ninja 的有效依赖记录中，已由 map 抽取的 tx_initialize_high_level.c.obj 和 tx_initialize_kernel_enter.c.obj 都实际包含此头。头文件没有自己的 .obj 或函数入口，不能靠在 ELF 符号表里搜索文件名判断是否使用。

第 13 层 / 组件初始化 / 文件 206

tx_initialize_high_level.c
建好内核的管理结构，还没有创建应用对象

已用 · ELF 抽取有效 33 行 / 物理 152 行条件宏与推荐裁前学习版源码common/src/tx_initialize_high_level.c ↗看裁剪版（有效 34 → 27 行）

问它初始化了哪一层，而不要只数括号。函数开头（113–129 行）先经过两个记录钩子；本配置中的 TX_TRACE_INITIALIZE（54–64 行） 和 TX_EL_INITIALIZE（2237–2250 行） 均为空。接下来的 _tx_thread_initialize、_tx_timer_initialize 才是真正的两个函数调用。前者准备调度器的就绪表和优先级信息；后者准备时钟和定时器链表。本例还在定时器组件内部（242–262 行）创建系统定时器线程，参数是 TX_DONT_START；别把它算进 Demo 创建的 8 个应用线程。

另六个调用长什么样？本例的 M4/GNU 端口（208–216 行）开启 TX_INLINE_INITIALIZATION；本文件在包含组件头之前（31–44 行）据此定义 TX_INVOKE_INLINE_INITIALIZATION。在未定义 TX_DISABLE_REDUNDANT_CLEARING 的这次构建中，函数后半段（131–150 行）按以下顺序使用六个宏：信号量（61–67 行）、队列（61–69 行）、事件标志（63–71 行）、块池（62–70 行）、字节池（74–82 行）、互斥锁（62–70 行）。每个宏清空本组件的已建对象链表头及数量，不调用一个同名的 C 函数。

拿队列作核对：_tx_queue_created_ptr 变为空、_tx_queue_created_count 变为零，只表示“内核尚未登记任何队列”。真正给 queue_0 指定消息大小和存储区的是后来由 208 调用的应用定义函数（146–150 行）。本文件既不调用 tx_application_define，也不进入调度器，做完即返回调用者。

本例使用证据

tx_initialize_high_level.c.obj 在 map 的归档抽取表中，最终 ELF 的函数指令地址为 0x00000808。对象的代码段只有两个函数调用重定位，分别指向线程和定时器初始化；另有 12 个数据地址引用，正好是六对链表头和计数。map 记下的抽取原因是低层汇编引用本文件定义的 _tx_initialize_unused_memory；这是链接依赖，不代表低层汇编调用了高层函数。

第 13 层 / 可选的提前初始化 / 文件 207

tx_initialize_kernel_setup.c
让启动代码先初始化内核，再返回给调用者

未直接用 · 仅入静态库有效 13 行 / 物理 102 行条件宏与推荐裁前学习版源码common/src/tx_initialize_kernel_setup.c ↗看裁剪版（有效 14 → 14 行）

这个 setup 是供启动代码选择的提前入口。文件说明（43–48 行）给出的场景是：有的编译器运行库在进入应用 main 之前就需要 ThreadX 的对象服务。没有这种启动调用时，不需要在 Demo 的 main 里补一行 setup()。

沿函数体从头读到返回（76–100 行）：写 IN_PROGRESS → 端口前置钩子 → _tx_initialize_low_level → _tx_initialize_high_level → 端口后置钩子 → 写 ALMOST_DONE。到此返回启动代码；它不调用应用定义函数，不启动调度器。这里的两个状态名是 205 中常量的后缀。

把它与 enter 的条件块及其后续（98–138 行）并排看：若已经是 ALMOST_DONE，208 跳过的是低层、高层及这一对前后置钩子；随后仍把状态写回 IN_PROGRESS，再调用应用。防止重复初始化的是 enter 的判断，不是 setup 自己先检查一遍。

本例使用证据

libthreadx.a 中有 tx_initialize_kernel_setup.c.obj，成员内也确有 _tx_initialize_kernel_setup 的函数体和对低层、高层的调用重定位。但 relink-01 的 map 没有抽取该成员，最终 ELF 没有该符号。本例的 CRT 转到 main（73–84 行），应用对象的 main 只引用 _tx_initialize_kernel_enter。这是“已编译、未链接”，不是“链接后猜它没运行”。

第 13 层 / 内核入口 / 文件 208

tx_initialize_kernel_enter.c
从应用的 main 进入，再把处理器交给调度器

已用 · ELF 抽取有效 35 行 / 物理 161 行条件宏与推荐裁前学习版源码common/src/tx_initialize_kernel_enter.c ↗看裁剪版（有效 36 → 27 行）

第一跳是宏，不是包装函数。main 的调用处（58–63 行）使用公开名 tx_kernel_enter；即便本例启用了 API 错误检查，实际生效的映射（1207–1214 行）仍直接指向 _tx_initialize_kernel_enter，没有 _txe_ 中转。tx_api.h（1587–1589 行） 是原型，带状态判断的 C 函数体（98–126 行）才是实现。本例初值不是 ALMOST_DONE，所以先走低层，再走高层，最后执行端口后置钩子。

第二跳从内核回到应用。越过条件块后，enter 重设状态并传入指针（128–142 行）。端口的 low_level 给 _tx_initialize_unused_memory 写入的是链接符号 __RAM_segment_used_end__ 所示地址再加 4；这里把指针的值交给 tx_application_define，不是指针变量自身的地址。Demo 声明了形参 first_unused_memory 却没有使用它：它用自己的全局数组 memory_area（25–29 行）去建字节池、取栈空间并创建线程 0（68–86 行）。端口提供了一块内存的起点，不等于应用必须在那里建池。

最后一跳才进入调度。应用完成对象创建并返回，enter 写 FINISHED 后调用 _tx_thread_schedule（140–153 行）。不要误把几个扩展点算作必经函数：本配置的 TX_INITIALIZE_KERNEL_ENTER_EXTENSION（1883–1889 行） 为空，调度前的执行分析开关也未启用。在 M4 调度入口（83–117 行），汇编清零 _tx_thread_preempt_disable、开中断、挂起 PendSV；处理程序取出待运行线程（200–207 行），再恢复上下文并异常返回（237–250 行）。enter 在正常路径不返回到 main。

本例使用证据

map 记载 Demo 对 _tx_initialize_kernel_enter 的引用抽取了 tx_initialize_kernel_enter.c.obj；ELF 中函数指令地址为 0x00000890。该对象代码段的四个直接调用重定位依次指向 _tx_initialize_low_level、_tx_initialize_high_level、tx_application_define、_tx_thread_schedule。后两者在此 ELF 的指令地址分别为 0x0000016E 和 0x00000690。这些地址是本次链接的结果，不是开发板烧录地址建议或上板执行记录。

串回应用 / 首次调度

队列创建得比线程晚，为什么这里没问题？

对照线程 1、2 的 TX_AUTO_START（92–104 行）和创建 queue_0 的位置（146–150 行）：它们都在同一次 tx_application_define 调用里。线程创建时，内核识别初始化上下文（273–286 行），沿恢复路径（325–329 行）把线程置为就绪；但首次调度还没开始。队列建好、应用定义函数返回，208 才把控制权交给端口。这个结论适用于这里的启动顺序，不能照搬到调度器已运行时的对象创建。

若想接着追到应用入口，从创建时填入线程初始栈的入口（206–211 行）读到线程外壳调用控制块里的入口指针（113–114 行）。Demo 有 8 个应用线程、6 个不同的入口函数（46–53 行）：3/4 共用一个，6/7 共用另一个。这与“谁在真实板上先执行”是两个问题；本页只用了源码和已有构建证据。
