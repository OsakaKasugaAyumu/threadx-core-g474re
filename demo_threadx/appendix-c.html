用线程和共享对象搭起一个应用

已用 · 直接链接有效 178 行 / 物理 370 行条件宏与推荐裁前学习版源码samples/demo_threadx.c ↗看裁剪版（有效 179 → 179 行）

这份文件只包含 tx_api.h：对象是普通 C 全局变量，线程和对象的创建也是手写的 C 调用，不用到 OIL、DTS 或生成目录里找。它没有 GPIO、UART 或板级初始化；它演示的是内核对象如何协作，不是某块 NUCLEO 板的外设例程。常量、控制块、计数器与入口声明（5–53 行）

先分清三种入口：谁调用谁？

  1. main 是 C 程序入口。附 B 的 C 启动代码调用它。它只做一件事：调用 tx_kernel_enter，不直接调用任何应用线程。main 函数体（58–63 行）
  2. tx_application_define 是内核调用的初始化函数。内核入口在调度开始前调用它。这里即使先创建线程、后创建队列也不矛盾：TX_AUTO_START 使创建成功的线程就绪，不是在这一行立即跳进线程。应用定义返回后，内核才进入调度器。应用回调与进入调度的位置（134–153 行）
  3. thread_…_entry 才是线程被调度后执行的应用代码。如果在 C 文件里找不到 tx_thread_create 的同名函数体，先点开本配置生效的创建宏（1402 行），再读参数检查 _txe_thread_create → 创建实现 _tx_thread_create。创建实现把入口与参数存进控制块，并为初始栈指定线程外壳；最终是外壳 _tx_thread_shell_entry调用这个控制块里的函数指针。从控制块取出入口和实参（112–115 行）

先有控制块，再给栈和缓冲区找内存

thread_0 到 thread_7 是 8 个独立的 TX_THREAD 变量；队列、信号量、互斥锁、事件标志组、两个内存池也各有自己的控制块。控制块不是栈，也不是消息的存储区。应用没有使用内核传入的 first_unused_memory，而是用自己的全局数组 memory_area 建立 byte_pool_0（9,120 字节）。建字节池、申请第一块栈、创建线程 0（68–86 行）

  • 8 个栈：每次创建线程前都从字节池按大小分配 1,024 字节，8 个栈共申请 8,192 字节。反复使用局部变量 pointer 只是用它接收每次的地址，不是让线程共用同一个栈。
  • 队列存储：再申请 100 × sizeof(ULONG)。本端口一个 ULONG 是 4 字节，所以这 400 字节可容纳 100 条单 ULONG 消息；TX_1_ULONG 指的是一条消息的长度，不是队列长度。分配缓冲并创建队列（146–150 行） · 内核如何计算队列容量
  • 块池存储：又从字节池取 100 字节，不是 100 个块，建立 block_pool_0，每块有效载荷为 sizeof(ULONG)。示例只在初始化时申请一个定长块，随即归还；队列里的消息并不来自这个块池。建块池、取块、还块（161–171 行）

这是示例的简写：初始化里的分配和创建没有逐次检查返回状态。上述数字是源码请求的大小，不是实测余量；也不能仅凭链接成功就判定每次分配都成功。

线程对照：按入口归并，看清哪两对共用代码

八次创建的完整参数（80–144 行）里，线程编号就是传给入口的 thread_input。每个线程的抢占阈值都等于自己的优先级；优先级数值越小越优先。表中的时间片以系统 tick 计；“无”表示 TX_NO_TIME_SLICE，不是禁止高优先级线程抢占。

沿同一对象追两端：传走了什么，谁在等？

1 / 2：队列传的是序号的值，不是它的地址

线程 1 把 thread_1_messages_sent 的地址交给 tx_queue_send，让内核复制当前的一个 ULONG，成功返回后才递增序号。线程 2 用 tx_queue_receive 收到局部变量 received_message；状态成功且值等于期望的 thread_2_messages_received 才递增期望值。两端都传 TX_WAIT_FOREVER：发送遇到满队列、接收遇到空队列时才需要等，不是每次调用都必然阻塞。循环入口的 thread_1_counter 在发送之前就加一，不能把它当作成功发送数。收发两端的序号与检查（204–254 行） · 内核发送 / 内核接收

3 / 4：计数信号量只给一个许可

semaphore_0 初值是 1。两个线程都先 get；取得许可的一方睡 2 tick 再 put。睡眠让出的是 CPU，并没有还许可；另一方此时若尝试获取就得等待。信号量记录可用数量，不像互斥锁那样记录哪条线程是所有者，这段代码也没有规定 3 和 4 必须轮流。初始计数（152–153 行） · 取许可、睡眠、归还（257–291 行） · 信号量 get / put 与唤醒

0 / 5：事件位表示“发生过”，不记录发生了几次

线程 0 先 tx_thread_sleep(10)，再用 TX_OR 把 event_flags_0 的 bit 0 置 1。线程 5 用 TX_OR_CLEAR 等掩码 0x1；满足时取回标志并清除请求位，再检查返回状态及 actual_flags 是否等于 0x1。同一位在被清除前置两次仍只是 1，不等于队列里的两条消息。线程 0 置位（178–201 行） · 线程 5 等待与核对（294–316 行） · 事件 set / get 与清位

读调用，不要只信注释：创建事件组旁的注释（155–156 行）写的是线程 1 和 5；实际调用 tx_event_flags_set 的是线程 0，线程 1 做的是队列发送。

6 / 7：同一所有者拿两次，要还两次

mutex_0 以 TX_NO_INHERIT 创建，关闭的是优先级继承，不是递归获取。第一个拿到锁的线程再次 get 同一把锁，持有次数从 1 变 2；持锁睡 2 tick 后，第一次 put 只把 2 减到 1，所有者不变。第二次 put 才解除它的所有权，有等待者时才可能移交。对照上一组信号量：那里的一份许可，并不能凭“上次是我拿的”再拿一次。互斥锁创建选项（158–159 行） · 两次获取与两次释放（336–368 行） · 同一所有者再获取 / 释放时检查持有次数

本例使用证据：如何从已有 ELF 核对“8 个线程、6 个入口”？

先认输入。out/compile_commands.json 将 samples/demo_threadx.c 对应到 demo_threadx.c.obj；relink-01/link.rsp 直接列出该对象，成功的 relink-01/demo_threadx.map 也有对应的 LOAD。这就是 C1 标记为“已用 · 直接链接”的原因，不是因为文件在 samples/ 目录中。

再看绑定。既有 relink-01/demo_threadx.elf 定义了 main、tx_application_define 和表中 6 个不同的线程入口。在应用定义的 8 个 _txe_thread_create 调用点逐个核对，控制块地址各异，入口参数从 0 到 7；线程 3 和 4 用同一个 Thumb 函数指针 0x0000054D，线程 6 和 7 共用 0x000005FD。另外 4 条线程各用各的入口。这比只数函数名多核对了一步：看的是每次创建到底传了谁。

最后看调用。应用对象中线程 0 对应 _tx_thread_sleep、_txe_event_flags_set；线程 5 对应 _txe_event_flags_get。共享互斥入口则是两次 _txe_mutex_get、一次 _tx_thread_sleep、两次 _txe_mutex_put。这些调用目标也与最终 ELF 一致。这是静态链接证据，不是线程切换顺序、API 成功返回或板上运行时长的证据。
