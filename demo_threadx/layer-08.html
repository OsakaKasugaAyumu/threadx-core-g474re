第一遍，只跟一条消息

先认出 111 的逐字复制宏，再按公开接口的调用方向往下读。txe_ 检查参数，真正拷贝消息、处理等待的是 tx_ 核心；本配置公开名的映射（1379–1389 行）能把二者接起来。

  1. 建队：初始化时提供后备区（146–150 行） → 114 检查 → 113 建立 100 个消息槽。
  2. 发送：线程 1 传入当前序号的地址（215–225 行） → 119 检查 → 118 入环或交给正在等的线程。
  3. 接收：线程 2 传入接收变量的地址（241–252 行） → 117 检查 → 116 复制或挂起；返回后，线程 2 核对状态和数值。

第二遍再看 115 的等待清理。后半章的队首发送、清空、通知、优先化和查询属于完整内核，不是 Demo 额外调用的 API。想先辨认“消息去了哪儿”，可跳到三条路径的状态推演。

第 08 层 / 等待清理、接收与发送 / 文件 115

tx_queue_cleanup.c
同一个清理回调，怎样区分“没消息”和“没空位”？

已用 · ELF 抽取有效 79 行 / 物理 227 行条件宏与推荐裁前学习版源码common/src/tx_queue_cleanup.c ↗看裁剪版（有效 80 → 64 行）

发送方等空位、接收方等消息，线程状态都叫 TX_QUEUE_SUSP。可中断配置下，先核对回调、当次挂起序号、队列 ID 和等待数（91–116 行），避免把过期请求当成当前等待；然后清回调、减少等待数并修补线程环（127–163 行）。这是在摘线程，不是在移动一条消息。

若线程仍为 TX_QUEUE_SUSP，按队列是否有消息设置超时结果并恢复线程（166–210 行）：有消息时，这一侧原本是在满队列等发送，返回 TX_QUEUE_FULL；无消息时是等接收，返回 TX_QUEUE_EMPTY。主动取消不同：通用取消代码先改状态并写 TX_WAIT_ABORTED（139–175 行），清理不应把它改写成超时。

接收器（400–415 行）和 发送器（307–322 行）均保存本函数地址，故它确实进入 ELF。Demo 两边都传 TX_WAIT_FOREVER：这允许挂起，但不会为这次等待启动有限时长的超时计时（130–149 行）。链接进来不是发生过超时的证据。

本例使用证据

既有 map 从 libthreadx.a 抽取 tx_queue_cleanup.c.obj；最终 ELF 中 _tx_queue_cleanup 的指令地址为 0x4f60。map 列出的引入者是接收对象；收、发两个已链接对象都引用这个清理回调，不能据此断言发生过超时。

tx_queue_receive.c
接收：先问队列是否有消息，再问谁在等

已用 · ELF 抽取有效 188 行 / 物理 488 行条件宏与推荐裁前学习版源码common/src/tx_queue_receive.c ↗看裁剪版（有效 189 → 160 行）

有消息、无人等时，从读游标复制一条到调用者的缓冲，再回绕游标、减入队数、加空位（120–156 行）。若队列是空的，TX_NO_WAIT 或禁止抢占时不能睡，返回 TX_QUEUE_EMPTY；可等待时，在线程里保存调用者的目的地址，排到等待环尾（400–444 行），再挂起，恢复后取完成状态（453–482 行）。下一位发送者可以直接写到这个目的地址。

若队列已满且有普通发送者在等，一次接收会复制两条不同的消息：先把原队首交给接收者（244–269 行），再从等待发送者的源地址复制到写游标并推进它（287–310 行），最后摘下该发送线程并以 TX_SUCCESS 恢复（314–365 行）。腾出的一槽随即补满，所以 enqueued 和 available_storage 都不变，而读、写游标都向前走了一条。

还有一个 Demo 不调用、完整内核却必须解释的分支：若等待链首的 tx_thread_suspend_option 为真，那是 120 的队首发送者。直接从其源地址复制到本次接收地址（164–186 行），再摘链并恢复它（190–241 行）；原来排在环里的队首消息留到下次接收。

DEMO / 跟踪一个 ULONG

同一对线程，三条可能的交付路径

线程 1 和线程 2 的创建参数（90–104 行）都是优先级 16、时间片 4 个 tick、自动启动。源码给出了它们能走的路径，并没有给出某次切换的实测顺序。下面是三种独立条件下的静态推演，不是运行轨迹；只考虑 Demo 的普通发送和接收，不加入队首发送、清空、删除或外部取消。

先算容量
DEMO_QUEUE_SIZE 是 100（7–10 行），不是 100 字节。应用申请并传入的字节数（146–150 行）是 100 × sizeof(ULONG) = 400 字节；它来自第 06 层字节池。本 M4/GNU 构建的 ULONG（113–120 行） 为 4 字节，TX_1_ULONG（150–154 行） 指每条 1 个字；容量为 400 ÷ 4 = 100 条。queue_0 控制块是单独的对象；不要套用第 07 层的块头开销。
① 有空位，无人等
设环为空、接收者还没等待。线程 1 发送值 0，118 把这个 ULONG 复制到第一个槽；已入队 / 可用槽从 0 / 100 → 1 / 99。之后线程 1 把自己的变量加一，不会改掉槽内的 0。线程 2 经 116 取回 0，两个数变回 0 / 100。这条消息经历了两次复制：应用 → 槽，槽 → 应用。
② 空队列，有人等收
假设此时线程 2 已在 116 中挂起，它的线程控制块保存了 &received_message。线程 1 到来时，118 将序号从源地址复制到该目的地址，设成功并恢复线程 2。只有一次消息复制；队列始终是 0 / 100，两个游标均不移动。线程 2 恢复后不需重新接收。
③ 满队列，有人等发
假设环中依次有 0…99，线程 1 因继续发送 100 而等待。线程 2 先取到最老的 0，116 随即从线程 1 暂存的源地址把 100 补到队尾，再恢复线程 1。环里变成 1…100；已入队 / 可用槽仍为 100 / 0。两次复制搬的是两条不同的消息，不是把刚取出的 0 放回去。

最后回到应用：发送方在成功返回后递增（215–225 行），接收方按值比对，再递增期望序号（233–252 行）。thread_1_counter、thread_2_counter 在调用前就加一，不能当成成功交付次数。

读完之后 / SELF-CHECK

用三个问题检验是否读通

  1. 哪个指针可能跨一次挂起继续被使用？空队列上的接收者留下目的地址，满队列上的发送者留下源地址，字段名都是 tx_thread_additional_suspend_info。关键在于 116 接收还是 118 发送把它写进去；要等到调用完成，应用才能把相应缓冲另作他用。
  2. 已入队数不变就说明没有收发吗？不能。上面②、③都是反例。128 状态查询读的是此刻有多少条，不是到现在为止交付了多少条。若再考虑 122 清空，发送者成功返回也不等于某个接收者处理过这条消息。
  3. 等待线程什么时候回到就绪状态？成功交付时，队列负责复制消息、摘下等待者并写入完成状态，通用内核负责挂起与恢复。恢复不等于立刻获得 CPU；不要从 map 或 ELF 推断线程切换的先后。
本层使用标记如何核实？

沿用 demo_threadx-01/relink-01 的 ELF、map，交叉核对静态库成员、最终符号和 Ninja 的实际包含依赖。应用入口 thread_1_entry / thread_2_entry 的指令地址分别为 0x04b0 / 0x04f8。23 份 = 1 个包含头 + 7 个抽取 C + 15 个仅入库 C；这说明哪些实现进入构建，不证明某一条分支曾在板上执行。
