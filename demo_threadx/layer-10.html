第一遍，只追一个对象的三个动作

把 event_flags_0 想成一组开关，而不是上一层会累计许可的信号量。在本端口，一个 ULONG 是 32 位；最低位为 1 表示事件 0 已置位，不记录它发生过几次。先对照 155 组件头 找到组内位图，再读下面三条调用线。目录的编号按依赖从底向上排，而这里的箭头按应用实际调用的方向走。

  1. 创建：应用创建 event_flags_0（155–156 行） → 158 检查对象和尺寸 → 157 清零并登记。
  2. 发送：线程 0 先睡 10 个 tick，再用 TX_OR 置位（189–199 行） → 163 检查 set 选项 → 162 改位并检查等待者。
  3. 等待：线程 5 用 TX_OR_CLEAR 等待 0x1（294–314 行） → 161 检查 get 参数 → 160 直接取位或登记等待。如果走了等待分支，最终由一次满足条件的 162 置位回写结果。

本配置的公开 API 映射（1350–1357 行）解释了为什么 ELF 大多先看到 _txe_ 检查包装。Demo 创建处的旧注释写的是“线程 1 和 5”；核对上面两处调用，实际置位的是线程 0，等待的是线程 5。第一次阅读可先略过通知和统计，试着回答：如果先置位、后等待，这个位还在吗？

tx_event_flags_set.c
置位：一个等待者直接交付，多个等待者按同一轮位图判断

已用 · ELF 抽取有效 262 行 / 物理 625 行条件宏与推荐裁前学习版源码common/src/tx_event_flags_set.c ↗看裁剪版（有效 263 → 232 行）

从set 的 AND 分支（131–180 行）和OR 分支（185–204 行）分开读。TX_AND 是保留掩码：当前值 0x3 与 0x2 相与后剩 0x2，不会把原先为 0 的位变为 1；遇到正在进行的扫描，可以先登记待清位。TX_OR 则把指定位置 1，并抵消这些位上尚未落实的清除。检查并满足等待者的是 OR 分支；没人等时，置好的位仍留在组里。

Demo 只有线程 5 会等这个组。若它已经挂起，快路径用该线程保存的掩码和选项判定（219–265 行），命中才先回写整组快照，再按 CLEAR 清位、摘链并记 TX_SUCCESS（271–294 行），随后调用通用恢复（296–312 行）。因此线程 5 回来时，输出可以是 0x1，组内当前值却已经是 0。

多人等待时，暂存等待环、取一份扫描位图并禁止线程抢占（319–346 行）。临时恢复中断；必要时从表头重扫并合入新置位（349–374 行）。每个仍在等的线程用扫描位图判断，CLEAR 则改组内位图（385–455 行），两者不是同一变量。因此，同一轮之前就等待同一位的两人，可能都因一次置位成功，而非“排在第一位的人独占”。超时或已中止的节点另行摘出，不伪造成功。还原等待环、应用延迟清位并恢复待处理线程（524–572 行）。最后恢复中断原状态，按需调用通知及检查抢占（599–619 行）；被恢复不等于此刻已执行到应用下一行。

DEMO / 线程 0 → 事件位 0 → 线程 5

看两条时间线：先等与先发，结果写在不同地方

线程 0 的创建参数（83–86 行）与线程 5 的创建参数（125–129 行）把两者设为自动启动，优先级分别为 1 和 4。前者睡 10 个 tick，等的是时间；后者的 TX_WAIT_FOREVER 等的是位，通用挂起对无限等待不启动超时定时器（129–142 行）。下面只画这一个组，不推断固定调度顺序，也不是板上采样。每对数字记作（组内当前位，等待线程数）。

起点：刚创建
（0x0，0）。为 event_flags_0 提供存储不等于设置了位；负责清零和登记它的是 157 创建核心。
路径 A · 线程 5 先等
（0x0，0）→（0x0，1）。160 获取先向输出地址写入当前快照 0；条件不满足，于是把这个地址随请求保存在挂起线程里。此时这次 get 还没返回，应用不能把 0 当成最终结果。
路径 A · 线程 0 后发
（0x0，1）→（0x0，0）。162 置位先得到 0x1，通过保存的地址把它写入线程 5 的 actual_flags，按 CLEAR 清去组内的位，再恢复等待者。线程 5 下次运行时，从原来的 get 拿到 TX_SUCCESS，不必再抢一次位。
路径 B · 线程 0 先发
（0x0，0）→（0x1，0）。没有等待者，位仍保留。线程 5 随后执行 get，160 在本次调用内写出 0x1 并清位：（0x1，0）→（0x0，0）。结果一样，区别是这个线程没有挂起，写出结果的不是 set。
对照 · 连发两次
假设无人等待，且两次 set(0x1, TX_OR) 之间没有清位：0x0 → 0x1 → 0x1。之后一次 get 并清位，就没有第二份 0x1 可取。若要逐次累计，这个位不能代替计数。

线程 5 的返回检查（305–314 行）写的是 actual_flags != 0x1，不只是测试最低位。原 Demo 只设置这一位，所以判断成立；若扩展示例同时保留了另一位，就不能把“整个返回值恰好等于掩码”当作“命中”的通用条件。

位运算 / 独立演算

同一个 0x3：用在 get 和 set，问题完全不同

假设每次演算都从组内位图 0x5（二进制 0101）重新开始，无人等待，没有延迟清位；掩码都是 0x3（0011）。下列不是 Demo 的额外调用。对照 160 判断与取位、162 修改位图 和 选项定义（144–149 行） 阅读。

get：任意命中
TX_OR：交集是 0x1，成功，输出整组 0x5，组内仍为 0x5。换成 TX_OR_CLEAR，输出仍为 0x5，但组内只剩 0x4；不相关的位没有清掉。
get：必须全中
TX_AND 或 TX_AND_CLEAR 加 TX_NO_WAIT：缺少 0x2，返回 TX_NO_EVENTS，输出快照仍为 0x5，组内不变。CLEAR 是成功后清除，不是无条件动作。
set：合入或保留
TX_OR 合入掩码，组内成为 0x7；TX_AND 保留掩码覆盖的旧位，组内成为 0x1。两者都不返回位图，只返回操作状态。set 不接受 TX_OR_CLEAR 或 TX_AND_CLEAR。

读完之后 / SELF-CHECK

合上源码，判断三种情况

  1. 线程被恢复，是否证明它收到了事件？不一定。162 命中等待写 TX_SUCCESS；159 有限等待超时写 TX_NO_EVENTS；170 删除组写 TX_DELETED。看保存的完成状态，不要仅凭线程离开等待环作结论。
  2. 若两个线程都已经用 CLEAR 等同一位，一次置位最多让一个成功吗？不是。没有其他干预时，162 的多人扫描用同一份扫描位图逐人判断；清除的是组内位图，所以两名已等待者都可成功。扫描完成后才发起的新 get，读到的则是清位后的组。这与普通信号量一次 put 交付给一个等待者不同。
  3. 线程 5 被唤醒，要先注册通知吗？不用。等待者的恢复来自位匹配和通用恢复服务。164 的通知回调是可选的另一条路径，本例没有注册。
