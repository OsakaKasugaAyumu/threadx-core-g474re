为什么不能只在 Demo 的 C 文件顶部加一个 define？

这是分别编译的库。应用、内核和确实读取这些条件的预处理汇编，要在看到头文件或首个测试前拿到一致的配置。tx_misra.c:32 在包含 tx_api.h 之前就检查 MISRA 宏；同样，tx_thread_initialize.c:26 会先选全局数据的归属。仅在应用定义，甚至仅在后读到的 tx_user.h 定义，都不能保证这些早期测试选对。

不采用第 215 份时，另做实验可把 -DTX_MISRA_ENABLE 当作独立配置的构建输入，而不能把这一行当作完整构建配方。M4/GNU 定义态的 tx_port.h:503 需要 _tx_misra_ipsr_get；本端口的汇编标签在 tx_misra.S:648。原例只将通用 tx_misra.c 编入库，未编译同名端口汇编；两份实现又有重名符号。不要把它们无条件一起加入，也不要认为有一份 C 文件就够。要按端口核对每个定义、未解析/重复符号和 ABI。

验证顺序：用实际编译命令看各代表单元的预处理结果（需要时用 -E -dM 看宏表）→ 查 nm 和 map 中的定义/抽取 → 反汇编核对真正的调用 → 重新验证 Demo。旧 ELF 不证明新配置通过。

怎样读数字、怎样看证据

214 = 208 份单核/端口 + 6 份配置、启动、链接和 Demo。逐一校对锁定清单的 SHA-256（214/214）。148 份直接写了条件，66 份没有。统计含 .c、.h、.S、.s、.ld；定义与模板可同字节但属不同来源，两个都保留。

先处理行续接、注释和字面量，再识别 #if/#ifdef/#ifndef/#elif。927 个起始条件块（497 个 ifdef、357 个 ifndef、73 个 if），另有 8 个 elif，共 935 处测试、144 个去重名字；203 个 else、927 个 endif 仅作配对。一个表达式可涉及多个宏，同名在不同文件只计一个名字。没有发现 GNU 汇编 .if…/.else/.endif 条件组。

不把注释、普通 #define、C 运行时 if、汇编执行时的条件跳转或 ld 的 ASSERT 计入。例：demo_threadx.c:7 的栈尺寸是数值常量；demo_threadx.c:159 的 TX_NO_INHERIT 是创建互斥锁时传入的策略值，不是全局编译开关。tx_port.h:155 的 TX_PORT_BASEPRI 是配套掩码值，不是本范围内独立被测试的条件名。

原例证据与静态推导分开。 “历史构建记录”来自已有的 附 A 构建记录、MISRA 对象及链接记录 和其他各层导读。原基线盘点时未取得其独立构建目录，未重新构建原配置。第 215 份另已完成 GNU 编译与链接；未进行硬件测量。端口默认值、注释模板和两个教学配置均标清来源；特别是 tx_user.h 自身只定义保护宏 TX_USER_H，这不排除命令行或端口另行定义其他宏。
