读完之后 / SELF-CHECK

不用背 API，拿三组状态做检查

  1. 创建成功 → 就绪 → 正在运行。查 027 写进 TCB 的用户入口，再找它交给建栈函数的另一个地址。只有处理器恢复外壳后，023 才调用用户函数。Demo 创建 8 个应用线程却只有 6 个不同的入口：3/4 共用一个，6/7 共用一个。内部定时器线程不是第九个应用线程。
  2. 睡眠、显式挂起、等对象。睡眠到期可由内核恢复；显式挂起要区分 resume 和撤销延迟挂起；等对象时，资源到达是成功交付，wait_abort 是打断等待。能解释 033 resume 和 035 wait_abort 为什么不可互换，就读懂了两种完全不同的“叫醒”。
  3. 完成／终止 → 复位或删除。自然返回是 TX_COMPLETED，显式终止是 TX_TERMINATED；049 reset 重建初始栈并停在显式挂起态，051 delete 则注销对象。这三步都不是“重新分配一块栈”。
如何复核“4 份已用、30 份未直接用”？

沿用 demo_threadx-01/relink-01 的既有 ELF 和 map，逐一比对 34 个源码哈希、静态库成员、map 的抽取表和最终 ELF 符号。所有 34 份均有归档成员；只有 023、027、028、030 被抽取。024 的对象没有同名函数定义；“有源文件”“有库成员”“有函数体”“进入 ELF”是不同层次。

编号按阅读顺序；行数按完整源文件，包含未选择的代码分支。每节的“上游原件”和行号都固定到同一个提交。站内导读离线可读；访问 GitHub 原件需要联网。链接证据不等于运行时覆盖，也不等于已在 VS Code 逐个验过 F12。
