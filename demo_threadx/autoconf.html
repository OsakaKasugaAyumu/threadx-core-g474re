一份头文件，选定一套内核分支

从 autoconf.h 开始读。它给内核、应用和预处理汇编提供同一套项目选择。你不必猜 TX_MISRA_ENABLE 在某个文件里到底开没开。

看裁剪版（配置头原字节保留）打开第 215 个源文件按文件和行号查实际分支 →这套配置选了什么在 VS Code 中看编译证据车载边界回到目录

先看 8 个由项目明确给定的值

TX_MISRA_ENABLE = 1
选择上游的 MISRA 写法。例如队列复制和初始化清零改走具名辅助函数；M4 端口派生 TX_DISABLE_INLINE。它不运行 MISRA 检查器，不代表整个 Demo 符合所有规则。
TX_SAFETY_CRITICAL = 1
独立于 MISRA：这次特意让 tx_api.h:2097 的安全选项检查实际参与编译，也保留上游演示异常路径。TX_ENABLE_STACK_CHECKING 不能在这个配置里一起开；保留栈填充不等同于运行时栈检查。
TX_INCLUDE_USER_DEFINE_FILE = 1
继续读取原例的 tx_user.h；锁定的原件没有生效的项目选项。项目只在新增头取值，不要再去不同的 .c 或 IDE 设置里抄一套。
TX_MAX_PRIORITIES = 32；TX_MINIMUM_STACK = 200
一个就绪优先级位图；200 字节是创建线程时的最低门槛，不是某个任务的栈预算。
TX_TIMER_THREAD_PRIORITY = 0；TX_TIMER_THREAD_STACK_SIZE = 1024；TX_TIMER_TICKS_PER_SECOND = 100UL
定时器线程用最高优先级、1024 字节示例栈；期望每秒 100 tick。启动汇编第 41–42 行另写了 6 MHz / 100；宏不会替你配置 G474RE 的时钟。

这些要保持未定义，不是定义成 0

TX_DISABLE_ERROR_CHECKING 不定义，所以公开 API 仍经 _txe_*；TX_TIMER_PROCESS_IN_ISR 不定义，超时交给定时器线程；TX_DISABLE_STACK_FILLING 不定义，保留栈填充。保持 PRIMASK，不引入 BASEPRI、Trace、性能计数、低功耗或外部执行钩子。所有禁止组合和覆盖均在配置头列出；#ifdef 只看“是否定义”，定义成 0 同样会进定义态。

读源码时，跟着这三处分叉走

  1. tx_misra.c:32 在包含 tx_api.h 之前就测 MISRA。翻到 #else 才是这次编译的定义态。只改 tx_user.h 太晚。这个 C 文件实际编译供阅读，但其中与端口重名的函数不是本 ELF 的实现。
  2. tx_port.h:212 派生非内联路径；第 501 行的 else 把系统状态读取映射到 _tx_misra_ipsr_get()。沿这个名字看 tx_misra.S:648，这才是本次链接的实现。
  3. tx_port.h:717 的 TX_THREAD_INIT 却不能全局统一定义：同一个头有时负责定义、有时只声明。原 214 份 935 处测试里，仅 4 处随包含现场而不同，涉及 TX_SOURCE_CODE 和 TX_THREAD_INIT；它们都不是项目配置开关。逐行结果区分选中、未选中和压根没求值，也报告完全没有直接条件的文件。

通用目标：怎样让 VS Code 看到编译器使用的宏

本节的入口生成通用目标和编辑器工作区，不是板级烧录入口。需要在 G474RE 上运行，直接用裁剪版编译烧录教程。

这是手工维护的、效果类似 Zephyr 配置头的项目文件；没有引入 Kconfig、DTS 或 west，也不会在编译后覆盖你读的头。只用 Python 3.9+ 与带 newlib/binutils 的 GNU Arm Embedded 工具链。命令从本仓库根目录执行：

py -3 tools/build_profile.py
py -3 tools/profile_branches.py
code build/gnu-m4f/threadx-m4f.code-workspace

若未找到编译器，给第一条命令追加 --gcc "完整路径/arm-none-eabi-gcc.exe"，或预设 THREADX_ARM_GCC。Linux 等可用 python3。只读源码可直接打开 HTML；不要把本机生成的编译数据库上传并让别人复用本机路径。

早期通用构建对每个 C 和 .S 用 -include autoconf.h（传入绝对路径），GNU 在读源文件第一行前就注入配置。小写 cortexm4_crt0.s 直接交给汇编器，demo_threadx.crt0.ld 交给链接器，这是早期运行的记录。当前裁前学习版的 214 份文件均在源码中显式包含 autoconf.h；当前通用构建也让小写 .s 和链接脚本经过预处理。C2 记录了这些包含现场。不要把 __GNUC__、__ARM_FP、组件初始化标记或头文件保护预定义成“配置”。

用 VS Code 的 Microsoft C/C++ 扩展打开生成的工作区：它指向实际编译器与 compile_commands.json。灰显和导航以当前翻译单元为准；不要打开含多个不同版本的上层目录。汇编同名实现应再对照 map，不把“能在编辑器点到一个符号”当作链接证据。已用独立的 VS Code 扩展主机（Microsoft C/C++ 1.27.7）实测三处 F12：tx_misra.c:32 → autoconf.h:27（MISRA）、tx_initialize_kernel_enter.c:42 → autoconf.h:28（安全限制）、tx_thread_initialize.c:89 → autoconf.h:30（优先级数）。这三项都定位到本仓库的定义，不代表 215 个文件每个使用点均已验收。

早期通用目标验证了什么

这里保留早期通用构建的记录，不是后来的板级 C3 或 C5 结果。固定不变的是原 214 份的历史来源清单，不是当前学习副本的字节。要复核当前副本，请看 C2 裁前与裁后哈希。

  • 该次通用构建使用 arm-none-eabi-gcc 14.3.1（STM32 工具包），显式选择 -mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard。ELF 属性为 ARMv7E-M、Thumb-2、VFPv4-D16、VFP 参数寄存器。
  • 编译 186 个 C + 12 个预处理汇编 + 1 个原样汇编。198 个经 CPP 的单元逐一验证了同一头的 8 个取值与禁止开关；199 条真实编译命令保存到 build/gnu-m4f/compile_commands.json。194 个内核/端口对象进入库；编入库不等于被 Demo 抽取。
  • ELF 里有 8 个应用线程的 6 个不同入口：thread_0_entry、thread_1_entry、thread_2_entry、thread_3_and_4_entry、thread_5_entry、thread_6_and_7_entry。还核对了 PendSV、SysTick、定时器线程、异常处理、_txe_thread_create 和 MISRA 辅助函数调用；未解析符号为 0。
  • 4 个反例都被拒绝：C 传 -DTX_MISRA_ENABLE=0、汇编传 -DTX_DISABLE_ERROR_CHECKING=0、把优先级覆写为 64、改用软浮点 ABI。分别证明“定义成 0”、逐文件覆盖和 ABI 漂移不会静默通过。
  • 分支重放对 198 个单元比对加标记和未加标记的预处理输出。报告显示编译期选择，不是运行时覆盖。运行脚本默认只更新本地证据；显式加 --write-site 才刷新站内分支页。

为什么不能把两份 tx_misra 一起链接？

可移植 C 与端口汇编都提供部分同名强符号。这份 Demo 只由 tx_misra.S 提供 MISRA 辅助函数；tx_misra.c 仅单独编译。它所提供、但本 Demo 没引用的 _tx_version_id 不在最终 ELF，不能把此归档当成任意应用的完整替换库。

原汇编把多个函数标签叠在同一条 BX LR 上。此 GNU 汇编器只给第一项标记 Thumb 函数，其余 31 项为 NOTYPE，直接链接会报目标类型未知。本项目专门为这 31 项传入 GNU 汇编器的 .type …, %function 声明：构建工具先核实它们与已有 Thumb 函数同址，再核对生成对象的符号类型、地址，以及修正前后 .text 和 .data 逐字节相同。该次汇编适配没有替换函数体、忽略重名/重定位错误，也没有改写历史来源原件。这是本学习构建的适配，不是上游认证构建步骤。

输出位于 build/gnu-m4f/：demo_threadx.elf、demo_threadx.map、verified.json、反汇编，以及重放后的 branches.json；不随站点发布。

它能用于车载学习，不能作为量产认证模板

本次能证明“同一组开关 + 一个确实链接的示例”，不能证明符合全部 MISRA 规则或 ISO 26262，也不能证明达到某个 ASIL 等级，也不能据此将通用 ELF 直接烧到 NUCLEO-G474RE。板级历史镜像及其实测另见 C5 报告。

这里的 TX_SAFETY_CRITICAL 默认异常响应是死循环，不能替具体 ECU 定义安全状态。原通用 Demo 初始化时也有未检查返回值的内存分配与线程创建。产品工程还要按分配的安全需求选择适用版本、端口、工具链与安全手册；审核故障响应、内存策略、栈与中断/时序预算，完成静态分析与偏差记录，以及目标硬件验证。读本不替这些活动签字。
