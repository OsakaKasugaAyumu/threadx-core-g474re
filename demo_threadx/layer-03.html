tx_timer_system_deactivate.c
等的东西提前来了，怎样撤销超时？

已用 · ELF 抽取有效 33 行 / 物理 134 行条件宏与推荐裁前学习版源码common/src/tx_timer_system_deactivate.c ↗看裁剪版（有效 34 → 34 行）

设一个线程正在做有期限的等待，而资源先于超时到达。恢复路径必须把它从定时链撤下，不能让旧节点以后再为同一次等待报到期。恢复前的定时检查（114–129 行） 会在节点仍挂链时调用 _tx_timer_system_deactivate；若没上链，就清剩余计数，避免尚未完成的挂起再登记它。

先判是否在链，再判是否独占（83–105 行）：tx_timer_internal_list_head 保存的是链头指针的位置。它为空就不必处理；若环上只有自己，且链头指向自己，就清掉链头。多节点摘链与头节点交接（108–131 行） 先接通前后邻居；若摘的是头，让下一节点接手链头，最后把被摘节点自己的 list_head 清空。整个过程不需要遍历时间轮。

这里修改的是定时器链，不是对象等待链，也不是就绪链。Demo 的队列收发用 TX_WAIT_FOREVER，不会因为这次队列等待登记有限超时；不要把上述“提前到达”的条件路径说成本例每次收发都会执行。

tx_thread_system_resume.c
从等待变成就绪，为何不一定马上运行？

已用 · ELF 抽取有效 476 行 / 物理 1004 行条件宏与推荐裁前学习版源码common/src/tx_thread_system_resume.c ↗看裁剪版（有效 477 → 115 行）

_tx_thread_system_resume 服务于内核的多种唤醒来源，不等同于应用的公开 tx_thread_resume。它先收尾超时（017），再判断线程是否已被摘出、是否已就绪、是否另有延迟挂起请求。这些检查及置 TX_READY 的位置（154–178 行） 说明“资源到了”并不保证线程立刻进入就绪链。

  1. 真要重新入链：同级为空时 建立自环并置就绪位（197–221 行）；非空时 接到原环尾（385–395 行），而不是插到原链头前抢走运行机会。
  2. 是否成为下一位：新出现的最高就绪级会更新 _tx_thread_highest_priority。若没有候选者可以直接指定；否则 把新优先级与候选线程的抢占阈值比较（221–249 行），符合条件才 替换 execute（303 行）。TX_READY 表示可被调度，不表示已经是 current。
  3. 若唤醒来早了：处理尚在挂起窗口的线程（409–445 行）。普通等待且没有延迟挂起时，原节点仍在就绪环，清掉 suspending 并恢复 TX_READY 即可；不能把同一个节点再插一遍。若另有延迟挂起请求，完成延迟挂起（399–405 行），结果可能是 TX_SUSPENDED。

回到 Demo：假设线程 2 已在空队列等待线程 1。发送者先 交付消息并写入接收成功状态（226–238 行），随后 恢复接收线程（255–262 行）。保证的是线程 2 以后继续执行时有数据可读，不是保证发送函数内立刻切到线程 2。

本例使用证据

map 记录此对象由内核静态库抽取；最终 ELF 中 _tx_thread_system_resume 的地址是 0x4818。队列发送、信号量释放及系统定时器线程的唤醒路径都引用这个实现。

读完之后 / SELF-CHECK

用两个断点问题把本层串起来

① 线程 0 的 10 个 tick 到了，下一条指令一定是设置事件标志吗？不是。到期回调先让它重新就绪，内核按优先级和抢占条件决定 execute；只有它真正获得 CPU 并从 tx_thread_sleep 返回，才会设置事件标志。睡满期限和获得 CPU 是两个时刻。

② 线程 2 在空队列里永久等消息，为什么系统不需要每个 tick 都检查它？它等在队列自己的名单上，不靠超时轮询。线程 1 发送时，队列找到等待者、交付消息并恢复它。若二者都已就绪且优先级相同，才进一步讨论时间片轮转。不存在“永远等待 = 永远不能被唤醒”。

这 8 个使用标记和端口分支怎样核对？

沿用 demo_threadx-01/relink-01 已有 ELF 与 map；8 个对象都由静态库抽取，8 个函数都在符号表。用实际 GCC 编译参数仅做预处理：32 级优先级、32 个定时槽，未启用 TX_NOT_INTERRUPTABLE、TX_TIMER_PROCESS_IN_ISR 或 TX_INLINE_THREAD_RESUME_SUSPEND。因此没有把不可中断版或 ISR 内处理方式算作本例路径。

反汇编的几个直接调用点：0x0a3c 从睡眠到系统挂起，0x0aa4 从挂起到定时登记，0x4a7c 从超时到系统恢复，0x483e 从系统恢复到定时撤销，0x4130 从队列发送到系统恢复。它们证明链接关系，不是上板轨迹，也不能证明每个分支都执行过。

范围是 8 个不同的通用内核 C 文件；文中提到的 Demo、端口头和其他层源码均为交叉引用，不重复计数。页内导读离线可读，固定提交的源码行链接需要联网。本批未进行 VS Code 逐符号跳转验收。
